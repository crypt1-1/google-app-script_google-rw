## 記載ルール

#### **※ 記録頻度と運用のルール（※**Project Milestones にも共通記載）

作業ログの鮮度と正確性を保つため、以下のタイミングと単位で記録・分離を行ってください。

詳細記録のタイミング:　　　#Project Milestones
	タスクが発生した時点から、一区切り（ステップごと）のスパンで細かくリアルタイムに記録を蓄積します。

ChangeLog（日報・日次サマリー）の確定:　　　#README/ChangeLog

※ 蓄積した詳細記録をベースに、その日の作業終了（日区切り）のタイミングでログ（Progress Update等）を確定・記載します。

### 日付 ＋ 管理 No. （Date:）の記述ルール

作業を記録・更新する都度、日付を必ず YYYY-MM-DD 形式で先頭に置き、その後ろに管理番号を記載します。

管理番号は全プロジェクトを通じて重複させず、1から1ずつ増やします。1〜9,999 は4桁、10,000以上は8桁のゼロ埋めで表示し、次の未使用番号を割り当てます。

### 【日付＋管理番号】

例: 2026-10-17_No.0001

- README の ChangeLog と、対応する Project Milestones の詳細記録には同じ管理番号を使う。
- 管理番号は全プロジェクト共通で重複不可。1から1ずつ増やし、次の未使用番号を割り当てる。
- 1〜9,999 は4桁ゼロ埋め（1 → 0001、9,999 → 9999）。
- 10,000以上は8桁ゼロ埋め（10,000 → 00010000）。
- 新着最上位（降順）: 新しい記録を上の行に追加する。

	ChangeLog の場合、日に数回記録するパターンとして、(例：Ph.1 ~ Ph.2) 等が想定される
 	または、同一プロジェクト内での別項目等 (例：PC 側 ⇨ Android 側)

#### タスク・プロジェクトの分離（別ファイル化の基準）:

同一ファイル内に複数のプロジェクトを混在させません。

現在のタスクやプロジェクトに区切りが付き、別の新しいタスクや別プロジェクトの作業が発生した場合は、必ず別の新しいテンプレート（ファイル）を作成して別途記載してください。

内容は、そのまま貼り付けられる形式で出力してください。

チャットで明確に示された事実と、そこから確実に読み取れる内容だけを記録してください。

#### Project Milestones と README は 1プロジェクトにそれぞれ 1ファイルセットで管理すること

## README の ChangeLog 記載形式

日付を先頭に置き、対応する詳細記録と同じ管理番号を使います。

```
[YYYY-MM-DD] 作業概要 - No.0001
tag: #Category #ProjectName
本日の作業概要:
- 仕様書の新設
- Template 作成
- 記載ルールの制定
- README の作成
- 命名規則の確定
```

### 概要

見出しと箇条書きで概要を短くまとめる

#### 追記ルール
- 新着最上位（降順）: 新しい記録（新しいNo.）を上の行に追加する。
- 管理No.の自動インクリメント: 記載した順に連番（No.nnn1, No.nnn2...）を登録する。

[2026-10-17] 運用ルールの策定および初期設定の実施 - No.0001
tag: #
今後の記録方針：
- プロジェクト記録: Project Milestones のソースとして作成する。
- 蓄積型: プロジェクト発生日をタイトルに設定する。
- 本文内の記録日: 記録する都度、日付 - 管理 No. を明記する。
- README（索引）: ChangeLog形式で記録概要を記載し、日付 - 管理 No. を明記し追記していく。
