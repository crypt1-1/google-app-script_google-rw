# 【記載ルール】Task 管理（課題・インシデント・運用タスク）

### 1. 目的と適用範囲

本ルールは、システムインシデント、ヘルスチェックで検知された課題、およびプロジェクトの運用タスクを正確に記録・追跡し、放置や手戻りを防ぐための共通ルールです。
すべてのタスクドキュメントおよび課題管理はこのフォーマットに従って記述します。

### 2. ファイルの保存場所と命名規則

- 保存先フォルダ: 09_Tasks
- ファイル名（Title）の命名規則:
	形式：Task_[YYYY-MM-DD]_No.[xxxx]_[Task-Title].md
	例：Task_2026-09-02_No.0001_NFS-Mount-Failure.md
	文字種制限：半角英数字と半角記号（_ - @ ! # $ ( ) ~）のみを使用し、空白や全角文字は含めません。

### 3. プライオリティ（重要度・優先度）の定義

課題やタスクは、システムや運用への影響度に応じて以下のプライオリティ（P1〜P3）に分類します。

| 優先度 | 定義・基準 | 対応の目安 / 状態 |
|---|---|---|
| P1 | 重大な障害・データ欠損・インシデント | 最優先対応（放置厳禁・即時エスカレーション） |
|---| （例：主要マウントの脱落、データ損失、RAGドメインの欠落など） |---|
| P2 | 機能不全・部分的影響・設定の不整合 | 早期対応（計画的な修正） |
|---| （例：ヘルスチェックの誤検知、一部マウントの不整合など） |---|
| P3 | 軽微な課題・監視・確認待ち事項 | 随時確認・監視 |
|---| （例：一時的な通信エラー、外部要因による停止、要ユーザー確認事項など） |---|

### 4. 状態（Status）の定義

タスクや課題のライフサイクルを表すステータスです。

- 未対応: 検知・起票されたが、まだ着手していない状態。
- 進行中: 現在原因調査または復旧作業を行っている状態。
- 確認待ち: ユーザーの判断、追加情報、外部要因の確認を待っている状態。
- 監視のみ: 復旧後、再発がないか様子を見ている状態。
- 解決済み: 対策が完了し、正常性が確認された状態。

### 5. Task ドキュメントの記載フォーマット（テンプレート）

タスクファイル内は、以下の構造とトーン＆マナー（客観的事実ベース、簡潔な箇条書き）で記述します。

```Markdown
# [Task-No.xxxx] タスク名・課題の概要
---
- **検出日**: YYYY-MM-DD
- **優先度**: P1 / P2 / P3
- **状態**: 未対応 / 進行中 / 確認待ち / 解決済み
- **管理番号**: No.xxxx
- **参照原本パス (Overview)**: https://drive.google.com/drive/folders/...

## 1. 課題・タスク詳細
- 発生している事象の客観的データや実測値を記載。
- 影響範囲（例：ドメイン欠落数、エラー件数など）。

## 2. 原因・背景
- 判明している原因や推定される要因。

## 3. 対応方針・アクション
- [ ] 実施すべき手順 1
- [ ] 実施すべき手順 2

## 4. 申し送り事項・特記事項
- 再発防止策や、次回のセッションへの引き継ぎ事項。
```

### 6. 運用チェックリスト（Task 管理編）

1. 一元管理の徹底：課題が発生した場合は、放置せず速やかに 09_Tasks 内に新規タスクファイルを作成すること。
2. 原本パスの埋め込み：すべてのタスクドキュメントには、必ず上位の Overview フォルダ等への参照原本パスを記載すること。
3. 機密情報の除外：パスワードやAPIトークンなどの秘匿情報は一切記載しないこと（確認用コマンドは当日中にクローズ・削除）。
4. ステータスの更新：状況が変化した際は速やかに「状態（Status）」を更新し、解決したものは「解決済み」セクションへ移行すること。
